# Resume state for ingredient-merges.csv

METHOD (do not deviate — this is what makes it accurate):
1. Read a slice of the sorted source with the Read tool:
   `docs/ingredients_sorted.tsv`
   (21,192 rows, `name<TAB>product_count`, sorted case-insensitively)
2. In the SAME turn, append pairs to docs/ingredient-merges.csv by copying
   strings verbatim from the slice. Never write a pair from memory of an
   earlier slice — that is how transcription errors get introduced.
3. Before using a canonical that is NOT visible in the current slice, confirm
   it exists:
   `awk -F'\t' -v k="NAME" '$1==k{c++}END{print c+0}' docs/ingredients_sorted.tsv`
   (Several plausible-looking canonicals do not exist — see the
   1,3-Butylene Glycol note below.)
4. Normalize, then validate, after every append:
   ```
   python3 scripts/ingredient_merges_normalize.py docs/ingredient-merges.csv
   python3 scripts/ingredient_merges_validate.py \
           docs/ingredients_sorted.tsv docs/ingredient-merges.csv
   ```
   Validate must report 0 for: variant not found / canonical not found /
   variant==canonical / merge chains / duplicate variant.

`ingredient_merges_normalize.py` drops duplicate variants (keeping the FIRST
occurrence and printing any that disagreed), forces tier 5 on `*`/`+`-only
differences, and collapses A->B->C chains. Slices overlap the earlier
targeted top-50 cluster sweep, so duplicates on append are expected and
harmless — normalize handles them.

FORMAT: variant|canonical|tier|confidence   (pipe-delimited; no name
contains a pipe. Names DO contain commas, hence not CSV commas.)
tier: 1 misspelling · 2 punctuation/format · 3 latin-vs-common · 4 qualifier
      or percentage suffix · 5 leading */+ artifact · 6 junk (canonical empty)
confidence: high (safe to apply) | review (needs a human/product decision)

## Confidence convention for tier 4 (settled 2026-07-20)
Earlier passes marked percentage-prefix strips (`3.0% Avobenzone`) `high`
while a later pass marked the identical suffix form (`Avobenzone 3.0%`)
`review`. Resolved in favour of the earlier, larger precedent:
- **high** — variant differs from canonical only by a concentration label
  (`2%`, `3.0 %`, `-2.5 %`) or a pharmacopoeia grade (`Usp`, `Nf`).
- **review** — descriptor qualifiers that are a product decision:
  `Organic`, `Solution`, `Clay`, `Anhydrous`, `Powder`, `Oil`, `L.`, etc.
Tier 3 (latin-vs-common, dual-INCI `X/Shea Butter` forms) stays `review`.

## Dual-INCI names: normalize among themselves, do not strip
`Beeswax/Cera Alba/Cire D'Abeille`, `Butyrospermum Parkii Butter/Shea Butter`,
`Cera Microcristallina/Microcrystalline Wax/Cire Microcristalline` etc. are
legitimate multi-language INCI labels. Fix their spacing/encoding/spelling
against the dominant form of the SAME dual name (tier 2, high); merging them
down to the bare name is tier 3 `review`.

## Gotcha: plain "Butylene Glycol" does not exist
The canonical is **`1,3-Butylene Glycol` (12,032 products — the single most
used ingredient in the table)**. All `Butylene Glyc*` typos point there and
are marked tier 3 `review`, because the merge also drops the `1,3-` prefix.

## Colour Index (CI) colorants
Two separate things, don't conflate them:
- **`Cl NNNNN` is lowercase L**, a typo family distinct from `CI NNNNN`
  (likewise `C142090`/`C177891` where `I` became `1`, and `CI17200` with the
  space dropped). These are tier 1/2 `high` merges into the `CI NNNNN` row.
- **`CI NNNNN / <US name>` dual forms** (`CI 77891/Titanium Dioxide`) merge
  to the bare `CI NNNNN`, tier 2 **`review`** — the trailing US name
  sometimes encodes a Lake/shade distinction that the CI number alone loses.
- **Multi-CI blends** (`CI 77491/77492/77499`) are NOT variants — left alone.
- Still open for a human: `CI 42090` and `Blue 1` are the same colorant under
  two naming conventions, and both are large rows. No merge written either
  way; earlier passes stripped the CI number (`Blue 1/Ci 42090` -> `Blue 1`),
  later ones strip the name — pick one convention before applying.

## US colorant names (D&C / Fd&C / Ext.)
Same problem as the CI block: five punctuation conventions for one name
(`D&C Red No. 33` / `D&C Red 33` / `D&C Red No.33` / `D&C Red No 33` /
`D&C Red #33`). All normalized to the dominant **`D&C <Color> No. <N>`** and
**`Fd&C <Color> No. <N>`** form, tier 2 `high`. Lake variants are kept as
their own canonical (`... No. 7 Lake`), never folded into the non-Lake row;
adding/removing a metal (`Ca`, `Aluminum`) is tier 2 `review`.
`Ext. Violet 2` is the canonical for the Ext. D&C Violet 2 family.

## Gotcha: don't write pairs from memory of a nearby cluster
Twice now a variant from one alphabetized cluster got mistyped onto a
similar-looking neighbour (`Lavender Oil*` invented from the `Lemon Oil*`
row; a `... Absolute` / `... Essential Oil*` canonical that only existed in
its asterisked form). The validator's "variant/canonical not found" catches
these — always run it and fix to 0 before moving on. Copy strings verbatim
from the CURRENT slice only.

## `Organic ` prefix — batch-handled (2026-07-20)
The entire `Organic <X>` family (rows ~13027-13829, but they're scattered)
was generated in ONE data-driven pass, NOT hand-copied: for every table row
starting `Organic `, strip the prefix (and any trailing `*`), and if the
remainder is itself a real table row, emit `Organic X|X|4|review`. 575 pairs.
This is safe because both strings come verbatim from the TSV and the
canonical's existence is checked against the TSV — no transcription/memory
risk. Skipped 228 `Organic X` rows whose plain `X` is not a standalone row.
If reusing the generator for other qualifier prefixes (`Certified Organic `,
`Cold Pressed `, `100% `, `Fresh `, `Kosher `), keep tier 4 `review`.

The `PEG ` -> `PEG-` space→hyphen family was batch-generated the same way
(38 pairs, tier 2 high): `re.match(r'^PEG (\d)', v)`, candidate `'PEG-'+v[4:]`,
emit only if candidate is a real row. Watch for self-refs when hand-adding
near a scripted batch (a `PEG-40 Sorbitan Peroleate|PEG-40 ...` slipped in
once; validator's variant==canonical catch flagged it).

Batched space↔hyphen families the same scripted way (verify DIRECTION by
count first — the canonical is whichever form has more products):
- `PEG N` → `PEG-N` (hyphen canonical), `Polyglyceryl N` → `Polyglyceryl-N`,
  `Polyquaternium N` → `Polyquaternium-N`, `PPG N` → `PPG-N`.
- **`Polysorbate` is REVERSED**: `Polysorbate-20` → `Polysorbate 20` (space
  form dominates: 5166 vs 237). Don't assume hyphen is always canonical.

### BUGFIX (first apply errored red): duplicate-PK on repoint
v1 did `DELETE colliding-with-existing` then `UPDATE variant->canonical`. That
missed the case where **one product lists two variants of the same canonical**
(e.g. `Water` + `Water/Aqua/Eau`, or `Tocopherol` + `Tocopherols`): the UPDATE
set both join rows to the same (product, canonical) -> unique-constraint
violation -> whole txn rolled back (nothing applied). v2 is collision-proof:
build `_repoint` = target rows GROUP BY (product, canonical) keeping MIN
position; DELETE all variant join rows; INSERT one canonical row per product
WHERE NOT EXISTS. Verified by simulating over the backup: **214 collisions
collapse cleanly**, result = 15,422 ingredients / 1,227,501 join rows, 0
canonicals dropped, 0 duplicate keys.
(Also: PostgREST CSV doubled backslashes in the 35 backslash ingredient names;
the DB truth is single-backslash `Water\Aqua\Eau` (verified via JSON), the
migration's SQL literals are single-backslash and match, and the backup CSV was
un-doubled so a \copy restore is accurate.)
